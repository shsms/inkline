* Features

** TODO Colours during C-r reverse search

While ~C-r~ (or ~C-s~) searches the history, the matched line is drawn
by readline alone, without colours: ~normal_editing()~ in ~src/ffi.rs~
treats ~RL_STATE_ISEARCH~ as busy, and inkline steps aside until the
search ends. The matched line should be coloured like any other line,
with the search prompt (~(reverse-i-search)`...':~) left as readline
draws it. Worth also marking the matched text within the line.

Things to check before starting:
- readline redraws the whole prompt on every key of the search, with a
  prompt of its own in place of the user's; the line may start on a
  different column than usual.
- no suggestion and no syntax underline while searching, only colours.
- the non-incremental searches (~RL_STATE_NSEARCH~, ~RL_STATE_SEARCH~)
  read their text as a line of their own, which should not be coloured
  as a command.
- bash 5.0, 5.2 and 5.3.

** TODO Show earlier accept errors when a later accept function refuses the line

When one function in ~inkline-accept-functions~ fails and a later one
refuses the line (~user-error~ or ~quit~), the line stays for editing
and only the refusal shows under it. The earlier function's error is
never shown: it would have been printed above the command's output,
but the command does not run. Show those errors too, after the refusal
text, joined with ~; ~ as the other hook messages are.

** TODO Colour a double-quoted script that holds a =$= expansion

=csvm "select amount > $min" data.csv= sends the script as typed, quote
marks included, because bash will still expand =$min= (a raw argument).
csvm then sees ="select= as its first word and colours nothing. Either
side could fix it: inkline could send the text inside the quotes with a
note of what is still expanded, or csvm could parse inside the quotes and
move each span one byte on (noted in csvm-rs's todo.org too).

** TODO Say when a helper never answers

A helper that is running but never replies costs up to 15 ms on every
key and shows no colour, with nothing to say why. Counting unanswered
requests and showing it in =inkline status= (or turning the helper off
after a while) would make this visible.

* Bugs

** TODO Keys typed ahead while inkline reload runs are sometimes lost

Keys typed while ~inkline reload~ runs, before the next prompt shows,
sometimes never reach the next line: they are dropped. It happens
without highlight helpers too. ~reload_stops_helpers~ in
~tests/helpers.rs~ waits for the next prompt before it types, to stay
clear of it.

Things to check: which step of the reload drops them (reading
~init.el~ again, binding the layout again, or setting readline's
variables), and whether something there sets the terminal up again in
a way that throws away input not yet read.

** TODO A deeply nested line overflows the stack

A line nested about 5,000 to 8,000 levels deep, such as ~"$(~ typed
over and over, overflows an 8 MB stack in ~args::commands~, which walks
the parse tree by calling itself for each level; ~Lexer::spans~ does
the same at about 16,000 levels. The overflow kills bash. Give both
walks a cap on the depth they go to.

** TODO A large request can hold up a redraw for a second

inkline writes a request to a helper in one go. When the request is
bigger than the socket can hold (about 180 KB for a socket pair on
Linux), such as a long script pasted as one argument, and the helper
reads slowly, the redraw waits for the helper to take the rest: up to
a second per helper (~SEND_WAIT~ in ~src/helper/process.rs~), after
which the helper is turned off (~request not read~). ~C-c~ ends the
wait within 20 ms, and turns the helper off too. Instead, keep the
part not sent yet and send the rest on later redraws, or while inkline
waits for a key, waiting on the socket until it can be written to as
well.

** TODO A helper's colours cover a =$( … )= inside a raw argument

inkline keeps bash's colour on =$var= inside an argument a helper colours,
but not on =$( … )= or backquotes: the helper's colours go over them. The
design says every bash expansion keeps bash's colour.

** TODO Helpers that ignore the end of their input are left running

A helper is only told to stop by the end of its input. One that ignores it
keeps running after =inkline reload=, after registering it again, and
after bash exits, and they add up.

** TODO A helper script with no =#!= line cannot start

inkline turns it off with "cannot run", where bash would run it with =sh=.

** TODO Known gaps in finding a command's words

These only cost colours: a backquote inside =${x:-…}=, =$`= in an unquoted
here-document body, =#= inside backquotes, a command on the same line as a
here-document start, and empty backquotes.

* Code

** TODO Write the "single function" check for hooks once

A hook's value is either one function or a list of them. The check for
"one function" is written twice: in Lisp as ~inkline--hook-single-p~
(used by ~add-hook~ and ~remove-hook~) and in Rust as
~is_single_function~ (used by ~functions~ and ~remove~), both in
~src/lisp/hooks.rs~. Register the Rust function as
~inkline--hook-single-p~ and drop the Lisp copy, so the two cannot
drift apart.

** TODO Indentation inside a multi-line csvm script

When Enter adds a line inside the quoted script of a command that has a
highlight helper (see ~docs/highlight-protocol.md~), ask the helper how far
to indent it, as inkline already does for bash code. The protocol leaves
room for this: a helper names ~indent~ on its first line
(~inkline-highlight 1 indent~), and only then does inkline send it an
~:indent~ request with the arguments and where the cursor is; the reply
says what to insert. Without an answer in time, keep the previous line's
indentation.

To settle first, as its own design: how a multi-line csvm script should
look (stages indented under the first line? each line starting with ~|~,
or ending with it? ~fn~ bodies?), and then the csvm rules that give it.
